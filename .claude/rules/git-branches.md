# Git 分支规则（etf-report 项目专属）

## 分支策略

- `main` — 唯一分支，所有改动在这里累积，也是 GitHub Actions + 腾讯云 SCF 的生产面

## 提交门禁

**git commit / git push 只能由用户触发，AI 不得自行发起。**

| 触发词 | 流程 | 说明 |
|--------|------|------|
| **"发布"** | `docs/runbook/release.md` 全流程（Phase 0-8） | 唯一合法提交时机，含版本治理 + 完整自检 |

**禁止行为**：

- AI 在用户未说"发布"时自行 `git commit`
- AI 在用户未说"发布"时自行 `git push`
- `git add -A`（必须指定文件或目录）
- **`git checkout -- <file>` / `git restore <file>` / `git reset --hard` — 禁止用于"回退改动"。这些操作无差别清除所有未提交改动（含用户自己写的代码），不可恢复**

**正确行为**：

- 改动完成后告知用户"有未提交改动，当前分支 main"，不主动 commit、不主动询问"要不要提交"
- 用户说"发布" → 走 release.md 全流程

## 提交节奏与发起权

### 原则

GitHub 远端（GitHub Actions + 腾讯云 SCF）是生产面，对远端稳定性要求极高。
commit/push 是**版本级**动作：一个版本内累积的所有改动，只在版本发布时由用户说
"发布"一次性提交。**绝不按需求 / 按 bug 逐个提交。**

### 版本前完整自检

自检的唯一事实源是 `docs/runbook/release.md`（Phase 0-6，含 `pytest tests` 全量
+ 安全审查 + 版本治理）。本规则不复制清单，只约束"何时能提交"。

### 禁止：主动询问"要不要提交"

- ❌ 每个需求/bug 完成后问"要我提交吗？""要不要把这几个文件一起提交？"
- ❌ 把"提交"作为选项塞进"下一步做什么"的 A/B/C 菜单
- ✅ 改动完成后只报告："有未提交改动，当前分支 main"，然后停

### 禁止：把"同意修代码"当成"授权提交"

- ❌ 用户说"同意"/"ok"/"依次执行"/"处理XX"（对修复/改动的确认）→ 顺手 commit + push
- ✅ "同意"只授权改代码。commit/push 必须等用户明确说"发布"
- 判定口诀：**改代码 ≠ 提交。授权范围不随任务推进自动扩大。**

### 为什么

远端是生产面，一次未验证/未收敛的提交推上去，直接影响每天 14:48 的实盘推送。
按需求逐个提交造成：① 历史碎片化，无法按版本回滚；② 未验证改动提前上生产；③ 失去"何时上生产"的控制权。

### 反例（本次会话实录）

- 用户说"同意"（同意修 BUG-067）→ AI 顺手 `committed + pushed to main`
- 用户说"那触发时间设置成 14:48 就好了" → AI 顺手 commit + push 文档
- 两处均无"发布"触发词，越权提交。

## 回退改动的正确方式

当用户说"回退刚才的改动"时，**禁止使用 `git checkout`**。必须：

1. **先 `git diff --stat`** — 确认哪些文件有未提交改动，每行改动是谁的
2. **定位 AI 的改动** — 用 `git diff <file>` 逐文件看，只回退 AI 产生的改动行
3. **用 `Edit` 逐条逆向** — 每条 Edit 都是精确的字符串替换，只影响一个逻辑块
4. **永远保留用户自己的未提交代码** — 即使看起来"顺手一起回退了更干净"也不行

`.git` 的作用是安全网：在动手之前用 `git diff` 看清楚范围，而不是在动手之后用 `git checkout` 核爆文件。
